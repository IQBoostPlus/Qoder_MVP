## 1. 功能需求

### FR-1 场景与数据

- **1.1** 三个模板：①夜间宿舍楼火灾 + 暴雨内涝；②实验室危化品泄漏 + 人员失联；③体育馆散场踩踏风险 + 通讯中断。
- **1.2** 每模板含起始楼栋、恶化条件、**≥2 个预案外意外变量**、标准动作集、关键待办清单。
- **1.3** 楼栋 **20 栋**，取自南京工程学院江宁校区真实建筑（选点清单见 §7），字段含名称、所属苑/园分区、类别、层数、估算容量、风险标注（变电/燃气/实验室）、邻接关系。路段单独建表，支持阻断。
- **1.4** 干扰因子：夜间、暴雨、通讯中断、人流高峰，以场景卡开关组合，不单设导调面板。

### FR-2 剧本生成（LLM）

- **2.1** 输入 = 模板 + 干扰因子 + 已入库楼栋；输出强约束 JSON：起始楼栋 id、时间轴节点、上报生成指令、关键项、标准动作集。
- **2.2** 楼栋 id 与动作 id 必须在 DB 中存在，无效引用丢弃并重生成。
- **2.3** Schema 校验失败在预算内重试 1 次；仍失败载入同模板兜底预生成剧本。
- **2.4** 任何情况下用户不得看到「生成失败」页。

### FR-3 模拟上报

- **3.1** 每轮 **10 条**，覆盖真报、误报、情绪化、位置模糊、重复五类。
- **3.2** 每条携带**事后真值**与**分时段合理判断**两套标签（见 §2.2）。
- **3.3** 全部落库带 `is_training = 1`，界面渲染「训练模拟数据」徽标。
- **3.4** 首版使用合成语料。如引入真实校园语料，先记录来源、移除姓名与联系方式及可识别细节，再说明改写方式。

### FR-4 回合、可见性与行动时机

- **4.1** 推演由回合组成，每回合对应一个时间轴节点 `t_k`。进入回合时投放所有 `appears_at_sim ≤ t_k` 且尚未投放的事件与上报。**未到的线索不得提前可见。**
- **4.2** 回合内学员可**任意顺序**判读已出现上报、改判、选楼栋、执行动作。**不要求判完整批才能行动。**
- **4.3** 动作完成时刻 = 提交时 `t_sim` + `duration_sim`。完成时刻晚于当前节点的，在后续回合显示完成，但记录的 `t_sim` 不变。
- **4.4** **整批优先级排序只在末回合开放**（剧本结束节点 `t_end`），此时全部上报已出现。
- **4.5** 加速播放只压缩真实等待，**不改变 `t_sim` 序列与动作 `duration_sim`**。
- **4.6** 学员真实操作耗时**不消耗模拟时间**，单独记录并展示，不计入总分。
- **4.7** **回合内所有操作**（判读、改判、定位、提交动作）的 `t_sim` 一律记为**当前回合节点的 `t_sim`**，不取真实时刻、不在节点之间插值。因此剧本节点列表必须覆盖样例中全部操作时刻；无新事件投放的回合列为「推进回合」，供学员犹豫或等待时使用。

### FR-5 处置动作与规则

- **5.1** 6 种动作，定义见 §5.1 动作目录。每种含适用对象、前置条件、`duration_sim`、资源消耗、权重。
- **5.2** 合法性由**规则引擎**判定，**不由 LLM 判定**。拒绝时说明原因并留痕，保留尝试序号。
- **5.3** 疏散路径由 **Dijkstra** 计算，阻断路段权重置 ∞，阻断实时反映在地图上。

### FR-6 评分与复盘

- **6.1** 四项指标按 §4 规则确定性计算，前后端复用同一份函数与常量。
- **6.2** 结束推演时**立即**渲染分数、分项明细与时间线；AI 文案异步补入，8 秒未返回显示预置摘要。
- **6.3** 点评每条引用具体动作序号，不允许泛泛而谈。
- **6.4** AI 不得输出「应当如何指挥真实事件」类表述：提示词层禁止 + 输出层关键词过滤。
- **6.5** 评分器与规则引擎必须有单元测试，用例见 [`quality-verification.md`](quality-verification.md)。

### FR-7 留痕与导出

- **7.1** `runs` 与 `run_events` 全量落库，按 `run_id` 导出完整事件与判定 JSON。
- **7.2** 本地「我的档案」列表展示时长、总分、主要失误类型。不做跨会话持久化看板。

### FR-8 体验与演示

- **8.1** 免登录，浏览器本地会话。2 个完整预置案例。
- **8.2** 「AI 随机生成」每会话限 3 次。
- **8.3** 演示模式一键载入已完成推演。**若某入口只能播放预录结果，必须标注「示例回放」**，不得与支持临场决策的入口混淆。

## 2. 数据契约

D1 上午冻结，写入 `src/contracts.ts` 与 `fixtures/`。

### 2.1 核心类型

```ts
Building      { id, name, zone, category, floors, capacity, risk_tag, polygon, adjacency: string[] }
RoadSegment   { id, from, to, blocked: boolean }   // from/to 引用 Building.id 或 Junction.id
Junction      { id, name, kind: 'gate'|'crossing' } // 校门与路口，非楼栋，不计入 20 栋
ActionDef     { id, name, applies_to, preconditions, duration_sim, cost, weight, critical }
Scenario      { id, template_id, modifiers, nodes: Node[], standard_actions, critical_items, t_end }
Node          { t_sim, events: Event[] }            // events 可为空 = 推进回合
RunEvent      { seq, t_sim, kind: 'disaster'|'ugc'|'action'|'verdict', payload }
ScoreResult   { discrimination, response, coverage, violation, total, breakdown }
```

`zone` 取真实分区名（萃园/润园/学海苑/至行苑/至和苑/文博苑/天健苑/至馨苑等），`floors` 取 §7 清单口径。`capacity` 为**模拟估算**，仅图书馆阅览座位数有公开资料支撑。

### 2.2 上报标签（v4 核心修正）

```ts
UgcReport {
  id
  appears_at_sim: number

  // 事后真值：客观锚点，用于复盘揭示与响应时长起点
  event_truth: {
    is_real: boolean
    locatable: boolean
    building_id: string | null   // locatable=false 时必须为 null
  }

  // 计分依据：基于当时可见线索的合理判断，随核实进展分段变化
  judgment_windows: Array<{
    from_sim: number
    to_sim: number | null        // null 表示直到结束
    expected: '真报' | '误报' | '待核'
    reason: string               // 复盘时向学员解释为何此时应这样判
  }>

  priority: number               // 1 最紧急，本轮内唯一，用于末回合排序
}
```

**判分规则**：学员提交判定的时刻 `judged_at_sim` 落在哪个 window，就与该 window 的 `expected` 比对。学员后续改判按**改判时刻**的 window 计分，覆盖前次。

**为什么必须分开**：一条事后证实为真的上报，在当时证据不足时选「待核」正是合理判断。v3 用二值 `is_real` 计分，会把这种正确判断判为错误。

**位置模糊 / 情绪化类**：`locatable = false`、`building_id = null`，学员选「无法定位」即为正确。定位正确率单独展示，不计入总分。

**`building_id` 是位置参考楼栋，不是处置对象**：界面只让学员选楼栋或「无法定位」。描述路段的上报（如样例 U9「北7东侧路面积水」）仍以其参照楼栋 N7 作为 `building_id`，真正的阻断对象由同回合的 `disaster` 事件单独引用路段 id。**定位与改道分别核对，不得把路段 id 塞进楼栋字段。**

### 2.3 数据表

```
campus_buildings, road_segments, disaster_templates, action_catalog
scenarios(source: generated|fallback)
runs, run_events, ugc_reports(is_training=1)
```

D1 定稿 DDL，D2 结束前冻结结构，之后只做增量变更，由 A、B 共同确认。

## 3. AI 边界与调用预算

**符号层管正确性**：Dijkstra 路径、规则引擎合法性、确定性评分。
**生成层管多样性**：剧本组合、噪声文本、复盘语言。

地图采用**自绘 SVG** 而非 Leaflet：零瓦片依赖、离线可演示、375px 下无拖拽与点选冲突、几何完全可控。代价是楼栋轮廓与路段几何全部人工构造，归 A。**建筑名称、分区、层数取自真实调研（§7），但平面位置与轮廓为训练级简化绘制，不代表实测坐标。** D1 即以 fixture 交付 8 栋供 B 先行开发，补齐至 20 栋时 B 无需改代码。精度声明为「训练级精度，楼栋位置人工绘制」。

### 调用预算（每轮上限 4 次）

| 用途 | 次数 |
| --- | --- |
| 剧本生成 | 1 |
| 整批上报生成 | 1 |
| 复盘文案 | 1 |
| 共享重试 | 1 |

- **请求发出即计数**，不以成功为准。
- 结构不合法或引用未知楼栋 → 丢弃无效结果，在预算内重试 1 次；仍失败载入兜底。
- 上报与复盘均备预置批次与基于得分明细的文字摘要，**断开 Agent 后仍能完成训练**。
- 调用计数随轮次记录。

### 「重新生成点评」的预算约束（v4 修正）

按钮启用需**同时**满足：

1. 原复盘请求已结束（成功、失败，或超时被判定为失败）；
2. 本轮剩余预算 ≥ 1。

否则按钮禁用并说明原因：

- 原请求仍在进行 → 「点评生成中」，**不发起新请求**；
- 预算已用完 → 「本轮模型预算已用完，当前显示基于得分明细的摘要」。

**典型场景**：剧本生成若已用掉共享重试（剧本 2 次），则上报 1 + 复盘 1 = 4，复盘无余量，超时后只能显示摘要，不可重新生成。v3 未约束此点，可能触发第 5 次调用。

## 4. 评分规则

四项均在 0～100，总加权和四舍五入取整。

| 指标 | 权重 | 换算 |
| --- | ---: | --- |
| 上报甄别准确率 | 30% | 按 §2.2 分时段规则核对主判定，正确条数 ÷ 本轮上报总数 × 100，未判计 0。改判按改判时刻计分。定位正确率单独展示，不计入 |
| 首报有效响应时长 | 20% | 起点 = **第一条 `event_truth.is_real = true` 的上报的 `appears_at_sim`**；终点 = 首个针对该事件且通过规则的动作**完成**的 `t_sim`。差值 ≤60 满分，60～240 线性降至 0，>240 或未响应计 0 |
| 标准动作命中率 | 35% | 已命中权重 ÷ 全部标准项权重 × 100，每项只计一次。权重见 §5.1 |
| 违规动作扣分 | 15% | 从 100 起，**同一动作在同一对象上被拒后再次提交**，每次扣 15，最低 0。首次被拒不计（允许合理探索）。不再单独扣遗漏——关键项遗漏已由命中率权重体现 |

**响应时长起点用事后真值而非合理判断**：这样「判待核 + 立即派核查」能同时拿甄别分与响应分，二者不冲突。

**违规项可达值**：100、85、70、55、40、25、10、0。**60 不可达**，v3 示例中的 60 已废弃。

## 5. D1 手算样例（双方共同交付）

**这是 D1 最重要的共同交付物**：一轮双方都能手算的样例。同一条「待核」上报、同一次核实、两种不同处置，各自对应明确的得分与复盘理由。A 用它验证引擎，B 用它验证界面，D6 联调时核对两侧结果一致。

落地为 `fixtures/canonical-run.json`（数据）+ `fixtures/canonical-run.md`（手算说明，即本节）。

### 5.1 动作目录（总权重 10）

| id | 动作 | 对象 | critical | 权重 | duration_sim |
| --- | --- | --- | --- | ---: | ---: |
| A1 | 上报核查 | 楼栋 | 否 | 1 | 45 |
| A2 | 派队 | 楼栋 | **是** | 3 | 60 |
| A3 | 警戒 | 楼栋周边 | **是** | 2 | 30 |
| A4 | 广播疏散 | 楼栋 | **是** | 2 | 20 |
| A5 | 封路 | 路段 | 否 | 1 | 25 |
| A6 | 断电 | 楼栋 | 否 | 1 | 35 |

**前置条件（规则引擎据此判定）**：

- **A4 广播疏散**：同楼栋 **A3 警戒已完成**。未满足则拒绝。
- **A6 断电**：对象存在灾情标注；同一楼栋不可重复执行。
- A1、A2、A3、A5 无前置条件。

两分支**成功执行**的动作均满足前置条件。分支乙在 t=150 提交的 A4 是**刻意安排的非法尝试**（A3 尚未完成），被拒后重复提交构成违规，不计入命中。

> 这条前置条件是样例的刻意设计：**警戒先于疏散**，否则广播会把人群引向未管控区域。分支甲做了 A3 却漏 A4，分支乙两者都迟做——两分支的失误因此都落在真实规则上，而不是靠违反前置条件凑分。

### 5.4 分支甲 · 推荐路径 → **83 分**

- 在 A3 警戒未完成时连续 3 次提交 A4 广播疏散，全部被拒；首次不计，后 2 次重复计违规。
- 情绪化（U4）与位置模糊（U5）误判为真报，夸大类（U10）未识别为误报。

### 5.6 样例的验收用途

- **A**：CLI 跑两分支，输出必须为 83 与 44，且分项与上表逐项一致。
- **B**：界面走两分支，显示的分数与复盘理由必须与上表一致。
- **D6 联调**：两侧结果一致即契约对齐成功。
- **加速恒定性**：分支甲在 1× 与 4× 速度下响应时长**均为 45 秒**。
- **临场可变性**：评委在分支甲基础上于 **t=150 回合补做 A4 广播疏散(N7)**，duration 20 → 完成 170；前置 A3 已于 130 完成，动作合法。命中率升至 100，总分变为 80×0.3 + 100×0.2 + 100×0.35 + 70×0.15 = 24+20+35+10.5 = 89.5 → **90**。**这是 D4 检查点的核心判据：分数必须随临场动作变化，预录流水做不到这一点。**
- **前置条件反证**：同一补做若放在 t=100 回合（A3 尚未完成，130 才完成），A4 应被拒绝，总分**仍为 83**。这一正一反两例共同证明规则引擎与评分器都在实时工作。
