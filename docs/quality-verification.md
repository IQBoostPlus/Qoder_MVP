### T1 测量协议（v4 修正）

v3 用「20～25 次点击」推算 3 分钟可达，**该推算不作为验收依据**——它把「选出三条」算作一次点击，也未计入选楼、阅读拒绝原因、改判与排序的实际耗时。

改为实测：

1. **D5**（fixture 版，公网）请 2 名未参与开发的同学独立操作，不解说、不提示。
2. 记录三项：**从打开网址到看见分数的实际用时**、**最耗时的一步**、**卡住或犹豫的位置**。
3. **D7**（集成版）用同样协议复测 2 人。
4. 结果填入下表。若 D7 仍超 3 分钟，触发 D7 检查点降级，并优先压缩最耗时的那一步，而不是继续推算点击数。

## 3. 评分器与规则引擎单元测试

**这是本项目唯一必须写测试的两处**（替代 v2 的「单页 ≤300 行」形式约束）。基准数据为 [`requirements.md` §5](requirements.md) 的 D1 手算样例，校园数据基准为同文档 §7。样例起始楼栋为 **N7（萃园 7 幢 / 北 7）**，阻断路段为 **R-N7E**。

### 3.1 评分基准用例

| 用例 | 输入 | 期望 |
| --- | --- | --- |
| SC-01 | 分支甲完整流水 | 甄别 80、响应 100、命中 80、违规 70，总分 **83**（命中失分项为**漏 A4 广播疏散**） |
| SC-02 | 分支乙完整流水 | 甄别 60、响应 0、命中 50、违规 55，总分 **44**（A2 与 A3 均完成于 280） |
| SC-03 | 分支甲 + 于 t=150 补做 **A4 广播疏散(N7)** | A3 已于 130 完成，动作合法；命中 100，总分 **90** |
| SC-03b | 分支甲 + 于 t=100 补做 A4（A3 尚未完成） | **拒绝**，命中仍 80，总分**仍为 83** |
| SC-04 | 同一流水重复计算 10 次 | 每次结果完全一致 |
| SC-05 | 违规次数 0～7 | 分项依次为 100、85、70、55、40、25、10、0；**断言 60 不可达** |

## 5. 三个检查点判据

| 时点 | 判据（可客观判定） | 不达标时 |
| --- | --- | --- |
| 🔴 **D1 晚** | Sites 建表、读写、Agent 调用三项连通性实测有结论 | DB 不通 → 本地 JSON + localStorage，契约不变，B 不受影响；Agent 不通 → 全部预置入库，B 不受影响 |
| 🔴 **D4 晚** | **同一固定剧本、两种选择，实时算出 83 与 44，分项与手算表逐项一致**；且于 t=150 补做 **A4** 后总分变为 **90**，于 t=100 补做 A4 则被拒、总分仍为 **83** | A 轨不通 → 优先保动作判定与评分器，B 接入同一剧本；B 轨不通 → CLI 引擎 + 极简表单页降级为对话式推演；只能预录 → 入口标「示例回放」，不得宣称支持临场决策 |
| 🔴 **D7 晚** | 公网可访问 + T1 实测达标 + 桌面与移动控制台 0 报错 | 移除 F11 档案列表，预置案例减为 1 个，砍除演示模式外的全部装饰 |

**D4 判据的设计理由**：预置流水只能证明一次既有结果，无法证明评委临场换个动作后分数也会变化。因此判据必须是「两种选择 → 两份不同结果」且为**实时计算**，并附**一正一反**两个临场改动验证（合法补做 A4 → 90；前置未满足时补做 A4 → 被拒、仍 83）。只有正向一例不足以区分「评分器在工作」与「评分器碰巧输出了另一个预置值」。这是降级预案最容易自欺的地方。
